## Principle

A recursive system must manage a continuing tradeoff between:

- preserving previously acquired information; and
- recomputing information when it is needed.

Insufficient preservation can cause repeated computation, increased latency, additional resource consumption, and loss of useful state.

Excessive preservation can cause storage growth, stale-state accumulation, retrieval overhead, reduced adaptability, and unnecessary architectural rigidity.

The **Memory–Compute Stability Minimum** is the operating region in which the combined burden of memory preservation, retrieval, recomputation, and correction is minimized while required system behavior remains within its declared constraints.

This minimum is not assumed to be a single universal constant. It is dependent on the system, workload, environment, time horizon, resource limits, and selected performance measures.

---

## Conceptual Representation

For a system configuration \(x\), define:

\[
C_{\text{total}}(x)
=
C_{\text{memory}}(x)
+
C_{\text{retrieval}}(x)
+
C_{\text{recompute}}(x)
+
C_{\text{correction}}(x)
\]

A candidate Memory–Compute Stability Minimum is a configuration \(x^*\) such that:

\[
x^*
=
\operatorname*{arg\,min}_{x \in \mathcal{F}}
C_{\text{total}}(x)
\]

where \(\mathcal{F}\) is the set of configurations satisfying the system’s declared functional, safety, fidelity, and resource constraints.

This expression is an engineering model. It does not by itself establish that every recursive system converges to a unique minimum.

## Required Evaluation Dimensions

A valid evaluation should declare, at minimum:

1. the information or state being preserved;
2. the cost assigned to storage and retention;
3. the cost assigned to indexing and retrieval;
4. the cost assigned to recomputation;
5. the cost of stale, corrupted, or conflicting memory;
6. the correction or validation cost;
7. the relevant workload and time horizon;
8. the applicable latency, energy, compute, and storage constraints;
9. the required fidelity or task-performance threshold;
10. the failure conditions that invalidate the proposed operating region.

The weighting and units used for these dimensions must be disclosed. Results obtained under different definitions or normalizations must not be treated as directly comparable without an explicit mapping.

## Engineering Relevance

The memory–compute tradeoff can be examined in systems using:

- retrieval-augmented generation;
- long-context processing;
- hierarchical memory;
- caching;
- state compression;
- world models;
- checkpointing;
- memoization;
- selective forgetting;
- summary-based persistence; and
- recomputation-based recovery.

These architectures may be interpreted as engineering responses to memory, retrieval, recomputation, and correction constraints.

Their existence does not independently prove the doctrine or establish that they share one universal causal mechanism.

---

## Minimum Evaluation Procedure

A benchmark or implementation invoking this doctrine should:

1. define a baseline without the proposed memory strategy;
2. identify the preserved state and its retention policy;
3. measure storage, retrieval, recomputation, and correction costs;
4. test multiple memory–compute configurations;
5. evaluate task performance and constraint satisfaction;
6. test behavior under distribution shift or stale-state conditions;
7. identify the lowest-cost feasible operating region;
8. report uncertainty, sensitivity, exclusions, and failure cases; and
9. compare the result with plausible alternative explanations or designs.

A result should not be described as a stability minimum merely because one tested configuration performs better than one baseline.
