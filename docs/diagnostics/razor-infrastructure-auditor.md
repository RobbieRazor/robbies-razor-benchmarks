## Purpose

The Razor Infrastructure Auditor examines evidence concerning whether a declared system appears to:

- reduce avoidable recursive burden;
- preserve reusable structure;
- reuse governed memory;
- control recomputation;
- operate within declared energy and infrastructure constraints;
- avoid unsupported Boundary Avoidance conclusions;
- document economic assumptions;
- identify possible collapse or instability signals.

The diagnostic produces review signals.

It does not automatically classify the system as stable, unstable, compliant, or non-compliant.

---

## Core Evaluation Principle

The diagnostic examines the proposition:

```text
Evaluate and reduce avoidable recursive burden
before attributing progress solely to infrastructure expansion.
```

Infrastructure expansion may be valid and necessary.

It should be evaluated according to measured utility, fidelity, provenance, accessibility, cost, governance burden, distortion, blast radius, and maintenance.

## Section 1 — Energetic Efficiency

### Question 1.1

Has Joules per Coherent Transition changed over the declared evaluation period?

```text
[ ] Decreased materially
[ ] Remained within declared tolerance
[ ] Increased materially
[ ] Unknown or not measured
[ ] Not applicable
```

Required evidence:

- definition of coherent transition
- energy boundary
- units
- measurement method
- workload
- baseline
- time interval
- uncertainty

Interpretation:

An increase is a review signal, not automatic proof of inefficiency or Boundary Avoidance. It may reflect changed task quality, additional verification, safety controls, workload differences, or measurement error.

---

### Question 1.2

Did additional compute change cost per declared useful output?

```text
[ ] Improved materially
[ ] No material change
[ ] Worsened materially
[ ] Mixed
[ ] Unknown or not measured
```

Define:

- useful output
- compute input
- task-quality boundary
- cost
- baseline
- tolerance

Additional compute is not automatically brute-force scaling.

## Section 2 — Memory and Inference Balance

### Question 2.1

```text
[ ] Not supported
[ ] Unknown
```

Evaluate preservation of:

- identity
- relationships

- version state
- retrieval paths
- evidence status

### Question 2.2

Has avoidable recomputation changed?

```text
[ ] Decreased materially
[ ] Remained stable
[ ] Increased materially
[ ] Mixed
[ ] Unknown
```

Distinguish necessary computation from avoidable reconstruction.

Possible measures include:

- repeated derivation
- repeated retrieval
- duplicated processing
- repeated verification
- token expansion
- correction demand

---

### Question 2.3

Has governed reuse changed?

```text
[ ] Increased materially
[ ] Remained stable
[ ] Decreased materially
[ ] Mixed
[ ] Unknown
```

Reuse should receive positive interpretation only when the reused structure remains sufficiently accurate, current, attributable, and appropriate to the task.

Repeated reuse of incorrect or stale structure is not a stability benefit.

## Provisional Diagnostic Profiles

### Profile A — Evidence of Alignment Within Tested Scope

Possible indicators:

- transition cost remains within declared bounds;
- required structure is preserved;
- governed reuse is demonstrated;
- avoidable recomputation is controlled;
- infrastructure expansion is justified by measured benefit;
- provenance and rollback controls are present.

This does not mean the system is universally stable, efficient, safe, or certified.

### Profile B — Mixed or Transitional Evidence

Possible indicators:

- inconsistent results across dimensions;
- partial preservation;
- incomplete measurement;
- unresolved review signals;
- workload-dependent behavior;
- improving but unverified controls.

This profile indicates that further investigation is required.

### Profile C — High-Concern Signals

Possible indicators:

- required structure is repeatedly lost;
- avoidable recomputation increases;
- correction demand grows;
- recursive depth produces measured instability;
- infrastructure expansion masks an unresolved internal burden;
- provenance or rollback controls are absent.

This is a diagnostic profile, not a regulatory non-compliance determination.

### Profile U — Insufficient Evidence

Use this profile when:

- required metrics are missing;
- baselines are absent;
- thresholds are undefined;
- results are not reproducible;
- relevant system boundaries are unknown.

Insufficient evidence must not be converted into Profile A, B, or C.

## Boundary Avoidance Requirement

Do not classify a system as Boundary Avoidance solely because it uses:

- more compute
- more energy
- more memory
- more infrastructure
- external services
- subsidies
- specialized hardware

A Boundary Avoidance diagnosis should demonstrate that:

1. an identifiable internal recursion cost or structural inefficiency exists;
2. external expansion displaces or masks that burden;
3. the expansion does not produce a sufficient measured internal improvement;
4. alternatives and counterevidence were considered.
