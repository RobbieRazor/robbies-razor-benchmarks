# 1. Purpose

The purpose of this document is to demonstrate how the orientation:

```text
compression
→ expression
→ memory
→ recursion
```

can generate structured questions about a bounded system.

The audit asks whether the system has adequately defined:

- what information is reduced or organized;
- what outputs or actions are expressed;
- what state is preserved;
- how preserved state is reused;
- what recursion is permitted;
- what constraints govern recursion;
- what happens when state is incorrect;
- how failures are detected and contained.

It does not presume the answers.

---

# 2. Structural Review vs Stability Determination

A structural review can identify:

- missing controls;
- unclear state ownership;
- unbounded permissions;
- weak provenance;
- uncontrolled retries;
- uncertain recovery.

Those findings may justify additional investigation.

They do not automatically establish:

```text
system instability
```

Required distinction:

```text
risk signal present
≠
failure observed
```

and:

```text
control absent
≠
failure inevitable
```

---

# 3. Domain-Neutral Does Not Mean Domain-Free

The historical version described the audit as usable:

```text
without requiring domain-specific assumptions
```

That is too broad.

The same review questions may sometimes be reused across domains, but meaningful evaluation still depends on domain-specific definitions.

For example:

```text
memory
```

means something different in:

- an AI agent;
- a database;
- an institution;
- a biological model.

Likewise:

```text
recursion
```

may refer to very different processes.

Therefore:

```text
general review template
≠
domain-independent diagnosis
```

Canonical orientation:

```text
RC-22 — Domain Transfer Constraint
```

# 5. Phase 1 — Compression Review

The compression review asks:

> Does the system transform information or state into a representation that is appropriate for later use while preserving required structure?

Possible questions include:

- What information is reduced?
- What is retained?
- What is discarded?
- What relationships must survive?
- What provenance must survive?
- What uncertainty must survive?
- What failure conditions invalidate the compressed representation?

Required distinction:

```text
smaller
≠
better
```

and:

```text
compression
≠
preservation automatically
```

---

# 6. Compression-Gate Boundary

A system does not necessarily require a literal:

```text
compression_gate
```

as a software component.

Compression may be implemented through:

- summarization;
- indexing;
- normalization;
- schemas;
- caching;
- filtering;
- structured representation;
- another mechanism.

Therefore:

```text
no explicit compression gate
≠
compression failure
```

The audit should examine function, not terminology.

---

# 7. Compression Failure Signals

Possible review signals may include:

- repeated reconstruction of unchanged information;
- loss of required provenance;
- representation growth without corresponding utility;
- omission of required relationships;
- distortion beyond tolerance.

These are signals.

They do not independently prove a Grand Compression failure mode.

---

# 8. Entropy Boundary

The historical version stated:

```text
Expression proceeds without compression,
leading to entropy growth.
```

That statement should not be retained without an explicitly defined entropy measure.

Possible entropy concepts include:

- Shannon entropy;
- output-distribution entropy;
- thermodynamic entropy;
- another formal measure.

Required distinction:

```text
representation growth
≠
entropy growth
```

unless the relevant entropy is operationally defined and measured.

---

# 9. Phase 2 — Expression Review

Expression refers to the production of an:

- output;
- action;
- representation;
- message;
- executable instruction;
- externally visible state.

The audit may ask:

- Is expression traceable to source state?
- Are constraints preserved?
- Can the output be validated?
- Is uncertainty represented?
- Does expression introduce unsupported information?

Expression quality must be evaluated separately from compression quality.

---

# 10. Expression Expansion Boundary

A system may generate large outputs for legitimate reasons.

Therefore:

```text
more expression
≠
structural failure
```

The appropriate comparison is:

```text
output burden
relative to
required utility and fidelity
```

---

# 11. Phase 3 — Memory Review

Memory refers to state preserved for later retrieval or reuse.

Possible memory structures include:

- persistent databases;
- caches;
- agent memory;
- logs;
- checkpoints;
- registries;
- model state;
- external retrieval stores.

The audit should identify exactly which form is being evaluated.

# 13. Memory Correctness Boundary

Persistent state is not necessarily valid state.

Required distinctions:

```text
stored
≠
correct
```

```text
retrieved
≠
verified
```

```text
high confidence
≠
truth
```

```text
memory hit
≠
revalidation
```

A strong memory system must also support invalidation, correction, or supersession where required.

---

# 14. Refresh-Cadence Boundary

The historical pseudocode treated:

```text
memory_refresh_interval
<
minimum_stable_interval
```

as evidence that memory might be erased.

No universal minimum stable interval exists.

A refresh may:

- improve freshness;
- erase needed history;
- preserve both current and historical state;
- have no relevant effect.

A review should instead ask:

> Does the update policy preserve the history and provenance required by the declared system?

---

# 15. Institutional-Amnesia Boundary

The phrase:

```text
institutional amnesia
```

may be used descriptively when required historical state becomes unavailable.

It should not be inferred merely because data is refreshed frequently.

Required distinction:

```text
frequent refresh
≠
memory loss
```

# 16. Phase 4 — Recursion Review

Recursion should be explicitly defined for the evaluated system.

Possible forms include:

- output becoming later input;
- repeated self-application;
- agent planning cycles;
- recursive retrieval;
- repeated state transformation.

Required distinction:

```text
repetition
≠
recursion automatically
```

---

# 17. Recursion-Rate Boundary

A variable such as:

```text
recursion_rate
```

has no meaning until its unit is defined.

Possible measures may include:

```text
recursive transitions / second
```

```text
agent cycles / task
```

```text
re-entry depth
```

A threshold must be justified by evidence rather than invented in an example implementation.

---

# 18. Recursion Throttling

Possible controls include:

- depth limits;
- rate limits;
- action quotas;
- retry ceilings;
- permission boundaries;
- cooldowns;
- stop conditions;
- independent validation.

These may reduce some risks.

But:

```text
throttle present
≠
system stable
```

and:

```text
throttle absent
≠
runaway behavior inevitable
```

Their effectiveness must be evaluated.

---

# 19. Runaway-Recursion Boundary

The historical file stated:

```text
Unthrottled recursion produces runaway behavior and instability.
```

That is too deterministic.

A bounded definition might instead use:

```text
runaway recursion
=
recursive activity that exceeds a declared resource,
depth, action, correction, or governance threshold
and continues without the intended stopping mechanism
```

Whether this occurs must be observed or tested.

---

# 20. Phase-Order Boundary

The historical version asked whether all four Razor phases were:

```text
present and correctly ordered
```

and implied that skipping phases causes collapse.

That should not be used as an automatic rule.

Real systems may:

- interleave phases;
- combine phases;
- omit explicit implementations of one phase;
- implement the same function through another architecture.

Required distinction:

```text
different implementation order
≠
Razor failure
```

The important question is whether the required functions and constraints remain satisfied.

---

# 21. Collapse Boundary

The historical file stated:

```text
Systems that skip phases appear efficient short-term
but collapse under scale.
```

A collapse claim requires:

- declared collapse variable;
- threshold;
- baseline;
- observed behavior;
- failure condition;
- uncertainty.

```text
COLLAPSE NOT ESTABLISHED
```

# 22. Governance Review

Governance may include:

- permissions;
- rate limits;
- approval mechanisms;
- schemas;
- validation;
- rollback;
- circuit breakers;
- human review;
- automated policy.

The audit asks whether governance is appropriate for the system’s:

- authority;
- risk;
- reversibility;
- blast radius;
- workload.

Governance architecture is not one-size-fits-all.

---

# 23. Governance Capacity Boundary

A system may have high recursion volume and still operate adequately if control capacity scales with it.

Likewise, low recursion volume can fail under weak controls.

Therefore:

```text
recursion rate
≠
governance adequacy
```

The relationship must be evaluated.

# 30. Illustrative Pseudocode

The following pseudocode is conceptual only.

It intentionally produces findings rather than a numerical stability verdict.

```python
class RazorGovernanceAudit:
    """
    Illustrative, non-operational structural review.

    This example does not certify stability,
    assign a universal score,
    or replace domain-specific evaluation.
    """

    def evaluate(self, system):
        findings = []
        missing_evidence = []

        # Compression / representation
        if not system.get("compression_method_defined", False):
            missing_evidence.append(
                "Compression or representation method not defined"
            )

        if system.get("required_provenance_lost", False):
            findings.append(
                "Required provenance loss observed"
            )

        # Memory
        if not system.get("memory_policy_defined", False):
            missing_evidence.append(
                "Memory preservation and invalidation policy not defined"
            )

        if system.get("stale_state_reused", False):
            findings.append(
                "Stale state was reused without declared revalidation"
            )

        # Recursion
        if not system.get("recursion_definition", None):
            missing_evidence.append(
                "Recursion variable or operation not defined"
            )

        if system.get("declared_recursion_limit_exceeded", False):
            findings.append(
                "Declared recursion limit exceeded"
            )

        # Governance / recovery
        if system.get("high_impact_actions", False) and not system.get(
            "recovery_mechanism_defined", False
        ):
            findings.append(
                "High-impact action path lacks declared recovery mechanism"
            )

        if missing_evidence:
            category = "INSUFFICIENT EVIDENCE"
        elif findings:
            category = "REVIEW SIGNAL"
        else:
            category = "NO MATERIAL SIGNAL DETECTED"

        return {
            "category": category,
            "findings": findings,
            "missing_evidence": missing_evidence,
            "certification": False,
        }
```

# 32. Alternative Explanations

Before interpreting a signal as a recursion-governance problem, consider alternatives such as:

- implementation defect;
- data error;
- distribution shift;
- changing workload;
- insufficient model capability;
- context truncation;
- retrieval failure;
- network failure;
- configuration error;
- measurement error.

A good audit documents why the selected interpretation is better supported than applicable alternatives.

---

# 33. False Positives

An audit may incorrectly flag a healthy design.

Examples:

- high recursion depth may be intentional and bounded;
- frequent memory refresh may preserve history correctly;
- infrastructure expansion may support new workload rather than mask inefficiency.

False-positive analysis should therefore be part of any formalized diagnostic.

---

# 34. False Negatives

An audit may also fail to identify real risks.

Examples:

- nominal recursion limits may be bypassable;
- apparently preserved memory may contain stale state;
- apparent isolation may fail under unusual dependencies.

A diagnostic should not be treated as complete merely because no signal appears.
